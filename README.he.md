# בונה תיקי נספחים

[English README](README.md)

אפליקציית Windows מקומית שמקבלת PDF של כתב תביעה ו-PDF-ים של נספחים, ומפיקה קובץ אחד מוגמר להגשה:
דף חוצץ לפני כל נספח, עמוד "נספחים / תוכן עניינים" עם טווחי עמודים, ומספור רץ אחיד על כל התיק.

המסמכים לא יוצאים מהמחשב. החלק שמטפל במסמכים חסום לרשת לגמרי, ברמת המערכת, ואינו כותב פרטי
תיק לקבצים זמניים. החריגה היחידה היא העדכונים האוטומטיים: הם רשאים לפנות לשרתי ההפצה של GitHub
ב-HTTPS, ולשום מקום אחר. ראו [עדכונים](#עדכונים).

## מבנה הפלט

```
עמודים 1..B      גוף כתב התביעה
עמוד  B+1        נספחים / תוכן עניינים   (יותר מעמוד אחד אם יש הרבה נספחים)
                 לכל נספח:
                   דף חוצץ אחד   "נספח N" / הכותרת / "עמ' X-Y"
                   עמודי הנספח
```

מספור רץ 1..N מוטבע בתחתית **כל** העמודים, כולל דפי החוצץ והנספחים הסרוקים.
דף החוצץ אינו נספר בטווח של הנספח שאחריו.

## התקנה

מורידים את `AppendixBuilder-Setup-<גרסה>.exe` מ[הגרסה האחרונה](https://github.com/YonatanVol/legal-appendix-builder/releases/latest)
ולוחצים עליו פעמיים. התוכנה מותקנת למשתמש הנוכחי בלבד, בלי הרשאות מנהל, נפתחת, ומקבלת קיצור
דרך בשולחן העבודה ובתפריט התחל.

התוכנה אינה חתומה דיגיטלית, ולכן בפעם הראשונה Windows מציג "Windows protected your PC". בוחרים
**More info** ואז **Run anyway**. עדכונים לא מציגים את זה שוב.

גרסה 1.2.0 הופצה כ-zip, ואצל המשתמשת הראשונה הופיע "ffmpeg.dll was not found" עוד לפני שנפתח
חלון: התוכנה טוענת את הקובץ הזה בעלייה, והיא הורצה בלי הקבצים שלצידה. מסיבה זו ההפצה היא עכשיו
קובץ התקנה.

## עדכונים

התוכנה המותקנת מתעדכנת לבד. כשמונה שניות אחרי הפתיחה, ואז כל ארבע שעות, היא שואלת את GitHub אם
יש גרסה חדשה. גרסה חדשה יורדת ברקע ומותקנת בפעם הבאה שסוגרים את התוכנה. פס בראש המסך מציע
להפעיל מחדש מיד, והפעלה מחדש נחסמת בזמן יצירת תיק. אחרי העדכון התוכנה אומרת לאיזו גרסה עודכנה
ומה חדש בה.

תוכנה שמתעדכנת לבד מריצה קוד שהגיע מהאינטרנט, ולכן כדאי לדייק במה שמגן עליה:

- **רק GitHub, רק HTTPS.** לעדכונים יש session נפרד מזה שמטפל במסמכים, ו-`src/main/security.js`
  מגביל אותו לשרתי ההפצה של GitHub. הצד של המסמכים נשאר בלי רשת. `test/security.js` מוכיח ששני
  הכללים מחוברים לסשנים שבאמת נמצאים בשימוש.
- **בדיקת checksum, לא חתימה.** כל מתקין נבדק מול ה-SHA-512 שמתפרסם לצידו ב-`latest.yml`. זה
  תופס הורדה פגומה או ששונתה. אבל שני הקבצים מגיעים מאותה גרסה, כך שזה לא עוזר אם הגרסה עצמה
  הוחלפה, ומכיוון שהתוכנה לא חתומה אין חתימת מפרסם לבדוק בנוסף.
- **ולכן חשבון GitHub הוא המפתח.** מי שמשתלט על החשבון, או יכול לדחוף תג `v*` למאגר הזה, יכול
  להפיץ קוד שירוץ אצל המשתמשת עם גישה לתיקי הלקוחות שלה. יש להשאיר אימות דו-שלבי בחשבון ולהגביל
  מי יוצר תגים. תעודת חתימת קוד הייתה מוסיפה את בדיקת החתימה החסרה ומעלימה את אזהרת SmartScreen.

התוכנה כותבת ל-`update.log` בתיקיית הנתונים שלה (`%APPDATA%\בונה תיקי נספחים`). ההגדרה
`APPENDIX_BUILDER_DISABLE_UPDATES=1` מכבה עדכונים.

## שימוש

1. גוררים את קובץ כתב התביעה לאזור העליון.
2. גוררים את קובצי הנספחים. כל קובץ הופך לנספח נפרד; אפשר לצרף קבצים נוספים לאותו נספח
   בכפתור "הוסף קובץ לנספח זה".
3. עורכים את הכותרות. הן מוצעות אוטומטית משם הקובץ וניתנות לשינוי חופשי.
   הכותרת היא מה שיופיע בתוכן העניינים ובדף החוצץ.
4. משנים סדר בחיצים. טווחי העמודים מתעדכנים מיד בכל שינוי, לפני ההפקה.
5. "צור תיק" ובוחרים היכן לשמור.

**חשוב:** יש לייצא את כתב התביעה מ-Word **ללא מספור עמודים**, כי התוכנה ממספרת את כל התיק בעצמה,
ומספור שנוסף ב-Word ייראה ככפילות.

## פתיחה חוזרת של תיק

כל תיק שמופק נרשם, ולשונית `היסטוריה` בצד פותחת את הרשימה. לחיצה על תיק מחזירה את מסך
העריכה כפי שהיה, כך שתיקון מכתב הוא החלפת קובץ אחד והפקה מחדש, ולא בחירה מחדש של הכל
והקלדה מחדש של כל הכותרות.

נשמר הסידור בלבד: אילו קבצים, באיזה סדר, תחת אילו כותרות. המסמכים נשארים היכן שהם. הם
מסמכים רפואיים, והעתקה שלהם לתיקייה של התוכנה הייתה עולה גם בפרטיות וגם במאות מגה-בייט לתיק.
מה שנעלם אחרי הפקה מעולם לא היה הקבצים.

- **הקבצים נקראים מחדש בכל פתיחה** ולא נשלפים מספרי עמודים שמורים. מכתב מתוקן הוא באורך אחר,
  ובלי קריאה מחדש כל הטווחים בתוכן העניינים היו יוצאים שגויים בלי שאיש ישים לב.
- **קובץ שהוזז אינו מפיל את הפתיחה.** הוא חוזר מסומן כחסר עם כפתור לאתר אותו, שאר התיק נטען,
  וההפקה חסומה עד שהוא נמצא, כששורת הסיכום אומרת זאת.

הרישום יושב בתיקיית הנתונים של המשתמש ומכיל נתיבים וכותרות נספחים, ובהם שמות לקוחות. זו אותה
חשיפה כמו המסמכים עצמם, חסימת הרשת חלה גם עליו, ואפשר למחוק כל שורה.

## דרישות מהקבצים

- PDF בלבד. קובץ שאינו PDF, פגום או ריק נדחה עם הודעה שמציינת איזה קובץ.
- קובץ מוגן בהצפנה נדחה. הפתרון: לפתוח בקורא PDF, "הדפס" ← "שמור כ-PDF", ולהעלות את הקובץ החדש.
  (התוכנה אינה מנסה לפענח, כדי לא לשלב עמודים משובשים בשקט.)
- עמודים מסובבים (`/Rotate`) נתמכים; המספור מוטבע במרכז התחתית החזותית ובכיוון הנכון.

## פיתוח

```
npm install
npm start          # מריץ את האפליקציה
npm test           # מריץ את כל הבדיקות המקומיות
```

**הגרסה ל-Windows נבנית על Windows**, ב-`.github/workflows/windows.yml`, בכל דחיפה. מהמק אי אפשר
עוד לבנות ל-Windows בכלל: ה-Wine וה-`makensis` של electron-builder הם בינאריים של Intel, וב-macOS 27
אין Rosetta. תהליך העבודה בונה את המתקין, מוודא שכל DLL שה-exe טוען בעלייה נמצא לצידו, מתקין אותו
בשקט, מפעיל את התוכנה המותקנת במצב בדיקה עצמית ומפיק תיק, בודק שהפעלה שנייה עוברת לחלון הפתוח,
ומוכיח עדכון מקצה לקצה: עדכון שזויף נדחה, עדכון אמיתי מותקן, והתוכנה המעודכנת עדיין עובדת.

אחרי כל גרסה, וגם פעם בשבוע, מכונת Windows מתקינה את הגרסה שפורסמה ושואלת את GitHub האמיתי אם
יש עדכון, דרך אותו כלל רשת. אם GitHub משנה את השרתים שמהם הוא מגיש קבצים, הבדיקה נכשלת ו-GitHub
שולח מייל, במקום שהתוכנה המותקנת תפסיק להתעדכן בשקט.

### גרסאות

קודם כותבים ב-[CHANGELOG.md](CHANGELOG.md) את ההערות לגרסה. הטקסט שלפני הכותרת `###` הראשונה
הוא מה שהמשתמשת רואה אחרי העדכון, ותהליך העבודה מסרב לפרסם גרסה בלעדיו. אחר כך:

```
npm version minor        # או patch: יוצר commit ותג v1.4.0
git push --follow-tags   # התהליך בודק את הגרסה על Windows ואז מפרסם אותה
```

התוכנות המותקנות קולטות את הגרסה בבדיקה הבאה שלהן. הגרסה מופיעה בכותרת החלון, בראש המסך, ובשם
קובץ ההתקנה.

### בדיקות

הבדיקות מבוססות על תיק אמיתי שהוגש (49 עמודים), שמפורק בחזרה לחלקיו ונבנה מחדש על ידי התוכנה.
כלומר יש תשובה נכונה ידועה להשוואה.

```
npm run split-reference "<נתיב לתיק הייחוס>"   # חותך אותו ל-test/fixtures (פעם אחת)
npm test
```

`test/fixtures/` אינו נכלל בבקרת גרסאות, כי הוא מכיל מסמכים רפואיים. אם התיקייה נמחקת יש לייצר
אותה מחדש מתיק הייחוס. הבדיקות משוות מול הפיקסצ'רים עצמם ולא מול קובץ המקור, כדי שלא יהיו תלויות
בקובץ שעלול להיעלם.

| בדיקה | מה נבדק |
|---|---|
| `test:build` + `test:verify` | בנייה מחדש של תיק הייחוס והשוואה מלאה מולו: 49 עמודים, טווחים, גדלי עמוד, ושימור טקסט הגוף והנספחים |
| `test:edge` | עמודים מסובבים בכל ארבע הזוויות, נספח מכמה קבצים, 26 נספחים שדוחפים את תוכן העניינים לעמוד שני, **כותרת שנשברת לשתי שורות והקו המנוקד שלה**, חריגה משוליים, וקלט פסול |
| `test:ui` | הממשק עצמו: הצעת כותרות, תצוגת טווחים חיה, שינוי סדר, חסימת הפקה בלי כותרת |
| `test:config` | הגדרות שבדיקה בזמן ריצה הייתה תופסת מאוחר מדי: כל מודול נארז, המתקין והתוכנה מסכימים על מזהה האפליקציה, גרסאות מתפרסמות רק מתג, ואין מקפים בטקסט בעברית |
| `test:updater-ui` | הודעות העדכון, כפתור ההפעלה מחדש, והתהליך הראשי שמסרב להפעיל מחדש באמצע יצירת תיק אמיתית |
| `test:security` | שני כללי הרשת אמיתיים ומחוברים לסשנים שבשימוש, ואף אחד מהם לא שובר את יצירת העמודים |
| `test:selftest` | הבדיקה העצמית של התוכנה, מקוד המקור; תהליך העבודה ב-Windows מריץ את אותה בדיקה על התוכנה המותקנת |

### למה Electron

העמודים המיוצרים מערבבים עברית עם ספרות ותאריכים (`עמ' 10-17`, `07/07/26`). ספריית PDF שמציירת טקסט
ישירות דורשת יישוב ידני של סדר הכתיבה הדו-כיווני, וטעויות שם מתגלות רק בעין. Electron כבר מכיל את מנוע
הטקסט של Chromium, ולכן דפי החוצץ ותוכן העניינים נכתבים כ-HTML ומודפסים ל-PDF. הסדר יוצא נכון,
והקו המנוקד הוא שורת CSS אחת.

### עיצוב העמודים המיוצרים

המידות נלקחו מקובצי Word שסופקו כדוגמה (`תוכן עניינים.docx`, `שער 2.docx`) ומופיעות בקוד ביחידות
נקודות, כך שהן עוברות אחד לאחד לעמוד המודפס:

| | גופן | גודל | משקל |
|---|---|---|---|
| כותרת "נספחים / תוכן עניינים" | David | 48pt | מודגש |
| שורת נספח בתוכן העניינים | David | 14pt | מודגש |
| "נספח N" בדף החוצץ | David | 26pt | מודגש + קו תחתון |
| כותרת וטווח בדף החוצץ | David | 26pt | רגיל |

שולי העמוד: 25mm בתוכן העניינים, 25mm/32mm בדף החוצץ.

הקו המנוקד בתוכן העניינים הוא רצף נקודות אמיתי באותו גופן, ולא קו CSS, בדיוק כמו במסמך המקור.
כותרת שאינה נכנסת לשורה אחת נשברת טבעית, והנקודות ממלאות את שארית **השורה האחרונה**, כמו טאב בוורד.

**הגופן נארז עם התוכנה** (`assets/fonts/`, גרסת Culmus של David) ואינו נלקח מ-Windows. ל-David
שמותקן ב-Windows יש הגבלת הטמעה: Chromium אינו רשאי להכניס אותו ל-PDF, ולכן הוא ממיר את האותיות
לקווי מתאר וקטוריים. העמוד נראה מושלם ואינו מכיל טקסט כלל, כך שתוכן העניינים ודפי החוצץ אינם
ניתנים לחיפוש, לסימון או להעתקה. לגרסה הארוזה `fsType = 0` והיא מוטמעת כרגיל.

האריזה גם מבטיחה רינדור זהה בכל מכונה, ולכן הבדיקות על מכונת הפיתוח בודקות את מה שנשלח בפועל.
`test/verify.js` מוודא במפורש שהגופן העברי מוטמע, וזו הבדיקה שהייתה תופסת את הבעיה מלכתחילה.

הערה: מספרי העמודים מוטבעים ב-Helvetica, אחד מארבעה-עשר הגופנים הסטנדרטיים של PDF שאינם מוטמעים
בהגדרה וקיימים בכל קורא. אם יידרש קובץ עצמאי לחלוטין (למשל לתקן PDF/A), יש להטביע גם אותם.

### שתי מלכודות שנפתרו בדרך

- `printToPDF` מקבל `pageSize` ב**אינצ'ים**. יחידה שגויה מייצרת עמודים גדולים פי אלפי מונים, בעוד הטקסט
  ממשיך להיחלץ מהם מושלם, ולכן גודל העמוד נבדק במפורש ב-`test/verify.js`.
- יצירה והשמדה של חלון לכל עמוד מייצרת כשל בעמוד השני ולעיתים קריסה. `render.js` מחזיק חלון מוסתר אחד
  ומשתמש בו מחדש.
- אין ב-CSS קופסה נמתחת בתוך זרימת טקסט, ולכן אורך הקו המנוקד נמדד ב-JavaScript אחרי הפריסה.
  כדי שהמדידה תהיה תקפה, `.sheet` מקבל **רוחב מפורש בנקודות** השווה לרוחב ההדפסה: בלוק ברוחב קבוע
  נפרס זהה בכל viewport, ולכן מה שנמדד על המסך הוא מה שיודפס. אחרי ההזרקה יש מעבר אימות שמקטין את
  מספר הנקודות אם השורה גדלה. הוספת נקודות לעולם לא מגדילה שורה.
- שולי עמוד חייבים לעבור ל-`printToPDF`, לא להיכתב כ-padding ב-CSS. Padding על בלוק שנפרס על כמה
  עמודים מיושם רק בתחילת הרצף ובסופו, ולכן תוכן עניינים שגולש לעמוד שני נחתך בתחתית. מסיבה זו גם אין
  כלל `@page { margin }` בתבניות, כי הוא היה גובר על השוליים שהמנוע מקבל.
